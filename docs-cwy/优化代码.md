## 2025-11-12: 环境变量方案

### 问题
4集群并行测试时，所有任务同时修改同一个 `aiopslab/config.yml` 文件，导致：
- 配置文件竞争（文件写入冲突）
- 任务读取到错误的集群配置
- Recovery阶段访问错误集群，抛出 `JSONDecodeError`
- 只有1个集群能成功，其他3个失败

**根本原因**: `get_kube_context()` 每次调用都重新读取 `config.yml`，在并发环境下读到被其他任务修改后的配置。

---

### 解决方案
增加环境变量支持，每个进程使用独立的环境变量指定集群，避免文件竞争。

---

### 修改详情

#### 1. `aiopslab/config.py` (+5行)

```python
def get_kube_context():
    """优先级: 环境变量 > kube_context > kind_cluster_name"""
    import os
    
    # 新增: 优先使用环境变量（用于并行执行）
    cluster_env = os.environ.get('AIOPSLAB_CLUSTER')
    if cluster_env:
        return f"kind-{cluster_env}"
    
    # 原有逻辑保持不变...
```

#### 2. `parallel_test_4_clusters.sh` (-7行)

**删除**:
```bash
CONFIG_BACKUP="/tmp/config_backup_${cluster}_$$.yml"
cp aiopslab/config.yml "$CONFIG_BACKUP"
sed -i 's/^kind_cluster_name:.*/kind_cluster_name: $cluster/' aiopslab/config.yml
sed -i 's/^k8s_host:.*/k8s_host: kind/' aiopslab/config.yml
mv "$CONFIG_BACKUP" aiopslab/config.yml
```

**替换为**:
```bash
export AIOPSLAB_CLUSTER="$cluster"
```

## 🐛 调试记录：wrk2 镜像问题

在4集群并行测试中，kind1/kind2/kind3 卡住的问题。

### 问题现象

- `kind` 集群成功完成
- `kind1/kind2/kind3` 卡在 "Job created: wrk2-job" 后无输出
- 进程存在但无进展，日志停止更新

### 调查过程

1. **检查日志**: `kind` 有 "Job completed successfully."，其他集群没有
2. **检查进程**: kind1/kind2/kind3 进程还在运行（但卡住）
3. **检查 wrk2-job**: 在 `default` namespace（不是 `test-social-network`）
4. **发现问题**: job 在 Running，但 pod 是 `ImagePullBackOff`

### 根本原因

```
kind1/kind2/kind3 缺少 deathstarbench/wrk2-client:latest 镜像
→ wrk2-job pod 启动失败（ImagePullBackOff）
→ job 永远不会变成 ready
→ wrk.py:114-122 的 while 循环永远卡住（等待 job_status.status.ready）
```

**错误信息**:
```
Failed to pull image "deathstarbench/wrk2-client:latest": 
proxyconnect tcp: dial tcp 127.0.0.1:8118: connect: connection refused
```

### 解决方案

```bash
# 1. 加载 wrk2-client 镜像到所有 Kind 集群
for cluster in kind1 kind2 kind3; do
    kind load docker-image deathstarbench/wrk2-client:latest --name $cluster
done

# 2. 删除失败的 job，让代码重新创建（代码会自动创建新的）
for cluster in kind1 kind2 kind3; do
    kubectl --context kind-$cluster delete job wrk2-job -n default
done

# 3. 等待30秒后，所有集群都成功完成 ✅
```

### 关键教训

1. **镜像检查要全面**: 
   - ❌ 只检查应用镜像（yg397/*）是不够的
   - ✅ 还要检查工具镜像：wrk2-client、alpine/git 等

2. **调试要深入**: 
   - kind 成功 ≠ 环境变量方案有问题
   - 可能是其他独立的基础设施问题

3. **命名空间很重要**: 
   - wrk2-job 在 `default` namespace
   - socialNetwork 应用在 `test-social-network` namespace
   - 不同的 namespace 容易遗漏

4. **多层次问题**: 
   ```
   第1层：配置冲突（环境变量解决）✅
   第2层：集群配置不完整（socialNetwork目录）✅
   第3层：镜像缺失（wrk2-client）✅ ← 本次修复
   ```

### 完整的镜像清单

创建新 Kind 集群时，需要确保以下镜像都已加载：

**应用镜像** (27个):
- 所有 `yg397/*` 的 socialNetwork 服务镜像

**基础设施镜像**:
- **OpenEBS**: `openebs/localpv-provisioner`, `openebs/linux-utils`, `openebs/node-disk-manager`, `openebs/node-disk-operator`, `openebs/node-disk-exporter`
- **Prometheus**: `quay.io/prometheus/*`, `registry.k8s.io/kube-state-metrics:v2.10.1`

**工具镜像** ⚠️ **容易遗漏**:
- `alpine/git:latest` - init容器用于拷贝源代码
- `deathstarbench/wrk2-client:latest` - 负载测试工具

### 自动化脚本建议

在 `create_new_kind_cluster.sh` 中添加 wrk2-client 镜像的加载：

```bash
# 在 "步骤2: 加载应用镜像" 之后添加
echo "步骤X: 加载工具镜像..."
kind load docker-image alpine/git:latest --name $CLUSTER_NAME
kind load docker-image deathstarbench/wrk2-client:latest --name $CLUSTER_NAME
```

## 2025-11-13: Chaos Mesh 镜像问题

### 根本原因
**`load_all_images.sh` 脚本不完整**：
- ✅ 包含了应用镜像（27个）
- ❌ **完全遗漏了 Chaos Mesh 镜像**（4个）
- ❌ 遗漏了 Prometheus 镜像（6个）
- ❌ 遗漏了 OpenEBS 镜像（5个）

**为什么遗漏**：
- Chaos Mesh 是动态安装的，在静态扫描镜像时被忽略

- 从未测试过 `kind1/kind2/kind3` 集群

### 解决方案

**1. 修改 `load_all_images.sh`**（+15个基础设施镜像）

```bash
    "ghcr.io/chaos-mesh/chaos-dashboard:v2.6.2"

    "openebs/provisioner-localpv:3.4.0"
    # ... 其他 4 个
    
    # === 应用镜像 ===
    # ... existing images ...

```

**2. 执行加载**

```bash

```

**3. 重启 Chaos Mesh pods**


### 效果

## Shell 环境变量支持

### 问题
在并行测试中发现，虽然 `kubectl` 和 `Helm` 命令使用了正确的集群，但 `Shell` 命令仍然在 `kind-control-plane` 容器执行，导致跨集群干扰。

### 根本原因

**文件**: `aiopslab/service/shell.py`

```python
if k8s_host == "kind":
    kind_cluster_name = config.get("kind_cluster_name", "kind")  # ❌ 硬编码
    container_name = f"{kind_cluster_name}-control-plane"
    return Shell.docker_exec(container_name, command)
```

**问题**: 没有读取 `AIOPSLAB_CLUSTER` 环境变量，导致：
- `kubectl` 命令 → 使用正确的集群 ✅
- `Shell` 命令 → 始终使用 `kind` 集群 ❌
- 同一任务的不同命令操作了不同的集群 ❌

### 解决方案

**修改 `shell.py`**（+7行）

```python
if k8s_host == "kind":
    # Priority 1: Environment variable (for parallel execution)
    cluster_env = os.environ.get('AIOPSLAB_CLUSTER')
    if cluster_env:
        kind_cluster_name = cluster_env
    else:
        # Priority 2: config.yml setting
        kind_cluster_name = config.get("kind_cluster_name", "kind")
    
    container_name = f"{kind_cluster_name}-control-plane"
    return Shell.docker_exec(container_name, command)
```

### 效果
- ✅ `Shell` 命令现在也使用正确的集群
- ✅ 完全隔离，无跨集群干扰
- ✅ 保持向后兼容

## 日志分离功能

### 问题
所有任务的输出都混在一个终端中，无法区分哪个任务的日志，难以调试。

### 解决方案

**修改 `service_api.py`**

**1. 添加导入**
```python
import sys
from pathlib import Path as FilePath
```

**2. 修改 `_run_single_episode` 函数**

```python
# 创建日志目录和文件
log_dir = FilePath("logs/echo") / job.job_id
log_dir.mkdir(parents=True, exist_ok=True)
log_file = log_dir / f"task_{problem_id}_{run_index}.log"

# 重定向 stdout/stderr 到日志文件
with open(log_file, 'a') as log_f:
    sys.stdout = log_f
    sys.stderr = log_f
    try:
        # service 调用...
    finally:
        sys.stdout = original_stdout
        sys.stderr = original_stderr
```

**3. 简化终端输出**

```python
# 任务开始
logger.info(f"▶ Task {problem_id}[{run_index}] started on cluster: {cluster_name}")

# 任务完成
logger.info(f"✅ Task {problem_id}[{run_index}] completed | Reward: {total_reward:.2f} | Steps: {step_index} | Log: {log_file}")

# 任务失败
logger.error(f"❌ Task {problem_id}[{run_index}] failed: {str(e)} | Log: {log_file}")
```

### 效果

**终端输出**（简洁）：
```
▶ Task container_kill-analysis-1[0] started on cluster: kind1
▶ Task container_kill-analysis-1[1] started on cluster: kind2
✅ Task container_kill-analysis-1[0] completed | Reward: 1.50 | Steps: 6
✅ Task container_kill-analysis-1[1] completed | Reward: 1.80 | Steps: 7
```

**日志文件结构**：
```
logs/echo/
├── {job_id_1}/
│   ├── task_container_kill-analysis-1_0.log
│   ├── task_container_kill-analysis-1_1.log
│   └── task_container_kill-detection-1_0.log
├── {job_id_2}/
│   └── task_xxx_0.log
```

- ✅ 终端简洁清晰，只显示关键信息
- ✅ 详细日志保存到文件，方便调试
- ✅ 按 job_id 和 task 自动组织目录结构
