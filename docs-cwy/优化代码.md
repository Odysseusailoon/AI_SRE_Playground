## 2025-11-12: 环境变量方案

### 问题
4集群并行测试时，所有任务同时修改同一个 `aiopslab/config.yml` 文件，导致：
- 配置文件竞争（文件写入冲突）
- 任务读取到错误的集群配置
- Recovery阶段访问错误集群，抛出 `JSONDecodeError`
- 只有1个集群能成功，其他3个失败

**根本原因**: `get_kube_context()` 每次调用都重新读取 `config.yml`，在并发环境下读到被其他任务修改后的配置。

---

### 解决方案
增加环境变量支持，每个进程使用独立的环境变量指定集群，避免文件竞争。

---

### 修改详情

#### 1. `aiopslab/config.py` (+5行)

```python
def get_kube_context():
    """优先级: 环境变量 > kube_context > kind_cluster_name"""
    import os
    
    # 新增: 优先使用环境变量（用于并行执行）
    cluster_env = os.environ.get('AIOPSLAB_CLUSTER')
    if cluster_env:
        return f"kind-{cluster_env}"
    
    # 原有逻辑保持不变...
```

#### 2. `parallel_test_4_clusters.sh` (-7行)

**删除**:
```bash
CONFIG_BACKUP="/tmp/config_backup_${cluster}_$$.yml"
cp aiopslab/config.yml "$CONFIG_BACKUP"
sed -i 's/^kind_cluster_name:.*/kind_cluster_name: $cluster/' aiopslab/config.yml
sed -i 's/^k8s_host:.*/k8s_host: kind/' aiopslab/config.yml
mv "$CONFIG_BACKUP" aiopslab/config.yml
```

**替换为**:
```bash
export AIOPSLAB_CLUSTER="$cluster"
```

## 🐛 调试记录：wrk2 镜像问题

在4集群并行测试中，kind1/kind2/kind3 卡住的问题。

### 问题现象

- `kind` 集群成功完成
- `kind1/kind2/kind3` 卡在 "Job created: wrk2-job" 后无输出
- 进程存在但无进展，日志停止更新

### 调查过程

1. **检查日志**: `kind` 有 "Job completed successfully."，其他集群没有
2. **检查进程**: kind1/kind2/kind3 进程还在运行（但卡住）
3. **检查 wrk2-job**: 在 `default` namespace（不是 `test-social-network`）
4. **发现问题**: job 在 Running，但 pod 是 `ImagePullBackOff`

### 根本原因

```
kind1/kind2/kind3 缺少 deathstarbench/wrk2-client:latest 镜像
→ wrk2-job pod 启动失败（ImagePullBackOff）
→ job 永远不会变成 ready
→ wrk.py:114-122 的 while 循环永远卡住（等待 job_status.status.ready）
```

**错误信息**:
```
Failed to pull image "deathstarbench/wrk2-client:latest": 
proxyconnect tcp: dial tcp 127.0.0.1:8118: connect: connection refused
```

### 解决方案

```bash
# 1. 加载 wrk2-client 镜像到所有 Kind 集群
for cluster in kind1 kind2 kind3; do
    kind load docker-image deathstarbench/wrk2-client:latest --name $cluster
done

# 2. 删除失败的 job，让代码重新创建（代码会自动创建新的）
for cluster in kind1 kind2 kind3; do
    kubectl --context kind-$cluster delete job wrk2-job -n default
done

# 3. 等待30秒后，所有集群都成功完成 ✅
```

### 关键教训

1. **镜像检查要全面**: 
   - ❌ 只检查应用镜像（yg397/*）是不够的
   - ✅ 还要检查工具镜像：wrk2-client、alpine/git 等

2. **调试要深入**: 
   - kind 成功 ≠ 环境变量方案有问题
   - 可能是其他独立的基础设施问题

3. **命名空间很重要**: 
   - wrk2-job 在 `default` namespace
   - socialNetwork 应用在 `test-social-network` namespace
   - 不同的 namespace 容易遗漏

4. **多层次问题**: 
   ```
   第1层：配置冲突（环境变量解决）✅
   第2层：集群配置不完整（socialNetwork目录）✅
   第3层：镜像缺失（wrk2-client）✅ ← 本次修复
   ```

### 完整的镜像清单

创建新 Kind 集群时，需要确保以下镜像都已加载：

**应用镜像** (27个):
- 所有 `yg397/*` 的 socialNetwork 服务镜像

**基础设施镜像**:
- **OpenEBS**: `openebs/localpv-provisioner`, `openebs/linux-utils`, `openebs/node-disk-manager`, `openebs/node-disk-operator`, `openebs/node-disk-exporter`
- **Prometheus**: `quay.io/prometheus/*`, `registry.k8s.io/kube-state-metrics:v2.10.1`

**工具镜像** ⚠️ **容易遗漏**:
- `alpine/git:latest` - init容器用于拷贝源代码
- `deathstarbench/wrk2-client:latest` - 负载测试工具

### 自动化脚本建议

在 `create_new_kind_cluster.sh` 中添加 wrk2-client 镜像的加载：


## Shell 环境变量支持

### 问题
在并行测试中发现，虽然 `kubectl` 和 `Helm` 命令使用了正确的集群，但 `Shell` 命令仍然在 `kind-control-plane` 容器执行，导致跨集群干扰。

### 根本原因

**文件**: `aiopslab/service/shell.py`

```python
if k8s_host == "kind":
    kind_cluster_name = config.get("kind_cluster_name", "kind")  # ❌ 硬编码
    container_name = f"{kind_cluster_name}-control-plane"
    return Shell.docker_exec(container_name, command)
```

**问题**: 没有读取 `AIOPSLAB_CLUSTER` 环境变量，导致：
- `kubectl` 命令 → 使用正确的集群 ✅
- `Shell` 命令 → 始终使用 `kind` 集群 ❌
- 同一任务的不同命令操作了不同的集群 ❌

### 解决方案

**修改 `shell.py`**（+7行）

```python
if k8s_host == "kind":
    # Priority 1: Environment variable (for parallel execution)
    cluster_env = os.environ.get('AIOPSLAB_CLUSTER')
    if cluster_env:
        kind_cluster_name = cluster_env
    else:
        # Priority 2: config.yml setting
        kind_cluster_name = config.get("kind_cluster_name", "kind")
    
    container_name = f"{kind_cluster_name}-control-plane"
    return Shell.docker_exec(container_name, command)
```

### 效果
- ✅ `Shell` 命令现在也使用正确的集群
- ✅ 完全隔离，无跨集群干扰
- ✅ 保持向后兼容

## 日志分离功能

### 问题
所有任务的输出都混在一个终端中，无法区分哪个任务的日志，难以调试。

### 解决方案

**修改 `service_api.py`**

**1. 添加导入**
```python
import sys
from pathlib import Path as FilePath
```

**2. 修改 `_run_single_episode` 函数**

```python
# 创建日志目录和文件
log_dir = FilePath("logs/echo") / job.job_id
log_dir.mkdir(parents=True, exist_ok=True)
log_file = log_dir / f"task_{problem_id}_{run_index}.log"

# 重定向 stdout/stderr 到日志文件
with open(log_file, 'a') as log_f:
    sys.stdout = log_f
    sys.stderr = log_f
    try:
        # service 调用...
    finally:
        sys.stdout = original_stdout
        sys.stderr = original_stderr
```

**3. 简化终端输出**

```python
# 任务开始
logger.info(f"▶ Task {problem_id}[{run_index}] started on cluster: {cluster_name}")

# 任务失败
logger.error(f"❌ Task {problem_id}[{run_index}] failed: {str(e)} | Log: {log_file}")
```

## 2025-11-19: Helm依赖优化

### 时间
2025-11-19 15:30

### 问题
并行测试时发现 `helm dependency update` 需要联网检查更新，导致：
- 每次启动耗时2-3分钟等待网络下载
- 依赖Chart版本使用通配符（`1.7.*`），必须联网确认最新版本
- 测试环境不需要实时更新，但每次都要等待

**根本原因**：
```bash
# aiopslab/service/helm.py:48
dependency_command = f"helm dependency update {chart_path}"
```

`helm dependency update` = 联网检查并下载最新版本

### 解决方案

**改动代码**（1行）：

```python
# 文件：aiopslab/service/helm.py
# 行：48

# 原代码
dependency_command = f"helm dependency update {chart_path}"

# 建议修改为
dependency_command = f"helm dependency build {chart_path}"
```

**差异对比**：

| 命令 | 行为 | 耗时 | 适用场景 |
|------|------|------|----------|
| `helm dependency update` | 联网检查最新版本 | 2-3分钟 | 生产环境 |
| `helm dependency build` | 直接使用本地已有 | 3-5秒 | 测试环境 |

### 原因分析

**1. Chart.yaml定义了版本范围**：
```yaml
dependencies:
  - name: alertmanager
    version: "1.7.*"   # 通配符！
    repository: https://prometheus-community.github.io/helm-charts
```

**2. update vs build**：
- `update`: 必须联网到`prometheus-community.github.io`查询`1.7.*`范围内的最新版本
- `build`: 直接使用`charts/`目录下已有的`.tgz`文件（已缓存）

**3. 本地已有依赖**：
```bash
$ ls aiopslab/observer/prometheus/prometheus/charts/
alertmanager-1.7.0.tgz
kube-state-metrics-5.15.3.tgz
prometheus-node-exporter-4.23.2.tgz
prometheus-pushgateway-2.4.2.tgz
```

### 效果

✅ **性能提升**：
- 从 2-3分钟 → 3-5秒（**提速40倍**）
- 避免网络依赖，离线环境可用

✅ **适用场景**：
- 测试环境（无需最新版本）
- 离线环境
- CI/CD流程加速

⚠️ **权衡**：
- 不会自动获取安全更新
- 需要手动定期执行 `helm dependency update` 更新缓存

### 建议

**测试环境**：
```python
# 使用 build（快速）
dependency_command = f"helm dependency build {chart_path}"
```

**生产环境**：
```python
# 使用 update（获取最新版本）
dependency_command = f"helm dependency update {chart_path}"
```

**或配置化**：
```python
# 根据环境变量选择
update_deps = os.environ.get('HELM_UPDATE_DEPS', 'false').lower() == 'true'
cmd = 'update' if update_deps else 'build'
dependency_command = f"helm dependency {cmd} {chart_path}"
```

### 状态
- ⏸️ **未提交PR**（需与上游讨论是否接受此优化）
- ✅ **测试环境可本地修改使用**

## 2025-11-19: Hotel Reservation Memcached版本统一

### 时间
2025-11-19 17:40

### 问题
在准备 kind11-86 集群批量创建时，发现 Hotel Reservation 应用的 memcached 部署文件存在版本不统一问题：
- `create_kinds_11_to_86.sh` 脚本中加载了两个memcached镜像：
  - `memcached:1.6.7` (明确版本)
  - `memcached:latest` (无tag版本)
- 但在 K8S YAML 文件中，3个 memcached deployment 使用了无版本标签的 `image: memcached`

**根本原因**：
```yaml
# hotelReservation/kubernetes/{profile,rate,reserve}/memcached-*-deployment.yaml
containers:
  - image: memcached  # ❌ 无版本标签，会尝试拉取latest
```

这会导致：
1. 集群尝试从网络拉取 `memcached:latest` 而不是使用本地已加载的 `memcached:1.6.7`
2. 离线环境下会失败
3. 版本不一致可能导致兼容性问题

### 解决方案

**修改 3 个 YAML 文件**，统一使用 `memcached:1.6.7`：

| 文件 | 路径 | 修改行 |
|-----|------|--------|
| memcached-profile-deployment.yaml | aiopslab-applications/hotelReservation/kubernetes/profile/ | 34 |
| memcached-rate-deployment.yaml | aiopslab-applications/hotelReservation/kubernetes/rate/ | 34 |
| memcached-reservation-deployment.yaml | aiopslab-applications/hotelReservation/kubernetes/reserve/ | 34 |

**修改内容**：
```yaml
# 修改前
containers:
  - image: memcached
    name: hotel-reserv-*-mmc

# 修改后  
containers:
  - image: memcached:1.6.7
    name: hotel-reserv-*-mmc
```

### 脚本优化

**`create_kinds_11_to_86.sh` 镜像列表**：
```bash
# 修改前（需要加载两个版本）
```

## 2025-11-19: tw_sock 缓存饱和导致 etcd 超时

### 时间
2025-11-19 23:00

### 问题现象
并行测试时，即使只运行 2 个 kind 集群（kind1 + kind2），也会出现：
- `kubectl` 命令超时：`TLS handshake timeout`
- etcd 连接超时：`read tcp 127.0.0.1:46838->127.0.0.1:2379: connection timed out`
- K8s 组件不断重启：
  - `kube-controller-manager`: 重启 172 次
  - `kube-scheduler`: 重启 171 次

### 根本原因

**tw_sock slab 缓存饱和**：

```
TCP 连接关闭后会产生 tw_sock 对象（TIME-WAIT socket）
→ 对象保存在内核 slab 缓存中
→ 默认保留 60 秒才过期
→ K8s 组件频繁重启产生大量短连接
→ tw_sock 缓存使用率达到 98-99%
→ 新建 socket 需要遍历 18,000+ 个对象查找空位
→ 分配耗时从 0.01秒 → 6秒
→ etcd 超时（默认 5秒）
→ K8s 组件健康检查失败被杀死
→ 组件重启产生更多连接
→ 恶性循环 ❌
```

**性能拐点**：

| tw_sock 使用率 | 分配速度 | 状态 |
|---------------|----------|------|
| 0-90% | 0.01-0.5秒 | ✅ 正常 |
| 90-95% | 0.5-2秒 | ⚠️ 偶尔慢 |
| 95-98% | 2-5秒 | ⚠️ 经常超时 |
| **98-99%** | **5-10秒** | ❌ **持续超时** |

**实际测量数据**：
```
kind1 容器：
  TCP alloc: 41,354
  tw_sock_TCP: 16,955 个 (使用率 98.0%)
  tw_sock_TCPv6: 15,314 个 (使用率 98.4%)
  
实际活跃连接：只有 47 个
僵尸对象：16,955 - 47 = 16,908 个（已过期但未释放）
```

### 解决方案

**方案 1：加速 tw_sock 过期** ⭐ **推荐**

```bash
# 修改参数（从 60秒 → 15秒）
docker exec kind1-control-plane sysctl -w net.ipv4.tcp_fin_timeout=15

# 批量应用到所有集群
for i in kind kind{1..86}; do
  docker exec ${i}-control-plane sysctl -w net.ipv4.tcp_fin_timeout=15 2>/dev/null &
done
```

**效果预期**：
- 使用率从 98% → 20-30%
- T+120秒后生效

**方案 2：按需启停集群** 💡 **长期方案**

```bash
# 平时停止，测试时启动
docker stop kind{1..86}-control-plane
docker start kind11-control-plane
docker exec kind11-control-plane sysctl -w net.ipv4.tcp_fin_timeout=15
```

### 🔍 深度调查：连接产生根源（2025-11-20 10:30）

**用户问题**：
1. 现在都没执行任务，为什么还在产生新连接？
2. 之前说的 "closed" 连接是什么，不能清空吗？

#### 调查结果

**问题 1：连接产生根源**

**根本原因**：**87 个 Kind 集群全部在运行**

即使不执行任务，每个 K8s 集群的组件都在持续运行：

| 活动类型 | 频率 | 87 集群总计 |
|---------|------|------------|
| 健康检查（kubelet → kube-apiserver → etcd） | 10 秒/次 | 522 次/分钟 |
| Pod 探活（kubelet → Pod） | 3-10 秒/次 | 1,740 次/分钟 |
| Prometheus 监控采集 | 15 秒/次 | 348 次/分钟 |
| 事件同步（controller/scheduler → apiserver） | 不定期 | 估计 500-1000 次/分钟 |
| **总计** | | **~5,220 次连接/分钟** |

**实测数据**：
```
宿主机总 TCP 连接：26,745 个
├─ kind1: 278 个
├─ kind2: 303 个
├─ kind10: 215 个
├─ ... (其他 84 个集群)
└─ 估算：87 × 250 = 21,750 个内部连接
```

**恶性循环**：
1. 87 集群产生 ~5,220 次连接/分钟
2. 每个连接关闭后进入 TIME-WAIT（15-60 秒）
3. tw_sock 缓存饱和（98-99%）
4. 新建 socket 变慢（0.01秒 → 5-10秒）
5. etcd/kube-apiserver 超时（5秒阈值）
6. 组件重试 → kube-apiserver 堆积 66 个到 etcd 的连接
7. etcd 被拖垮（响应时间 0.01秒 → 2分12秒）
8. 组件崩溃重启 → 更多连接
9. 循环加剧 ❌

**问题 2：关于 "closed" 连接**

**澄清**：这些连接**不是真的 "CLOSED"**，而是：

| 状态 | 数量（kind1） | 含义 | 能否清空？ |
|------|--------------|------|-----------|
| **TIME-WAIT** | 72 | 连接已关闭，等待内核回收（15-60秒） | ❌ 不能 |
| **SYN-SENT** | 22 | 正在尝试建立但卡住的连接 | ❌ 不能 |
| **ESTAB** | 192 | 正常的已建立连接 | ❌ 不能 |

**为什么不能手动清空？**

1. **TIME-WAIT 是 TCP 协议规定的必经状态**：
   - 目的：防止旧连接的延迟数据包干扰新连接
   - 持续时间：由 `tcp_fin_timeout` 控制（已改为 15 秒）
   - 内核会自动回收，无法手动强制清空

2. **tw_sock 是内核 slab 缓存**：
   - 没有 `clear cache` 命令
   - 强制清空会导致 TCP 协议栈混乱：
     - 端口冲突（新连接可能复用旧端口）
     - 数据包错乱（旧连接的延迟包干扰新连接）
     - 连接状态不一致

3. **唯一有效方法**：
   - 减少新连接产生速度
   - 让回收速度 > 产生速度
   - tw_sock 使用率自然下降
